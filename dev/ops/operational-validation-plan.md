# 운영 검증 기준과 측정 계약

## 1. 목적

이 문서는 로드맵 13-1부터 13-7까지 수행할 운영 검증의 비교 기준을
소유한다. 성능 수치는 코드뿐 아니라 서버 사양, 데이터 크기, 실행 프로세스
수와 부하 발생 방식에 따라 달라진다. 따라서 결과를 보기 전에 검증 범위와
고정 조건을 기록하고, 조건이 달라진 실행은 별도 실험으로 취급한다.

관련 문서:

- 기능 범위: `docs/functional-specification-v2.md` 13장
- 실행 순서: `docs/functional-specification-v2-roadmap.md` 13장
- 비용·종료 기준: `dev/ops/portfolio-deployment-cost-runbook.md`
- 배포 구조: `dev/ops/portfolio-runtime-runbook.md`

## 2. 기준 버전

| 구분 | commit | 의미 |
|---|---|---|
| 마지막 운영 스모크 테스트 배포 | `002fc171d8ebec57957b4c86d0179b338768334b` | 13-0에서 실제 EC2 기능 연결을 확인한 버전 |
| 현재 기능 기준선 | `a486bc3920a42d13bfa4eea7c63b7aae4f2eea87` | UI/UX 최종화를 포함해 13-1을 시작한 `dev` HEAD |
| 최초 성능 기준 측정 | 13-2 계측 완료 뒤 run manifest에 기록 | OpenTelemetry를 포함한 실제 기준 부하 버전 |
| 병목 개선 재측정 | 13-6-8 완료 뒤 run manifest에 기록 | 기준 측정에서 찾은 병목 한 건만 개선한 버전 |

`002fc17`은 현재 기능 기준선의 조상이며 과거 배포 증거다. 앞으로 수행하는
성능 비교는 `002fc17`과 하지 않는다. 13-2의 계측 변경을 포함한 최초 측정
commit과 13-6-8의 단일 개선 commit을 비교한다.

각 실행은 짧은 hash가 아니라 전체 commit SHA를 결과 manifest에 남긴다.
측정 도중 코드나 런타임 설정이 바뀌면 같은 run으로 이어서 기록하지 않는다.

## 3. 검증에 포함하는 기능

관리자 기능을 제외한 현재 사용자 기능을 검증한다.

1. 이메일·비밀번호 가입, 이메일 확인, 로그인, 세션, 비밀번호 변경·재설정
2. 게임 등록·수정, 분류, 플레이 링크, 공개 목록·검색·상세 조회
3. 프로필, 팔로우와 관심 게임
4. 크레딧 원장, 리뷰 요청·배정·제출·평가와 리뷰어 평판
5. 키 배포 예약·재고·대기실·입장 허용·암호화된 키 지급
6. Outbox, RabbitMQ, Worker, 웹·실시간·SES 알림
7. R2 직접 업로드, Worker 이미지 처리, 공개 조회와 삭제
8. Nginx HTTPS, Web·Worker systemd와 PostgreSQL·Redis·RabbitMQ 실행 경계

일반 부하는 공개 조회·검색, 집중 부하는 대기실·키 수령을 대표 시나리오로
사용한다. 알림과 미디어는 사용자 부하의 후속 비동기 처리량과 장애 복구를
별도로 관측한다.

## 4. 검증에서 제외하거나 제한하는 범위

| 항목 | 처리 |
|---|---|
| 로드맵 5 관리자 기능 | 미구현이므로 출시 판단 범위에서 제외 |
| Google 로그인 | 제품 기능은 유지하지만 원시 IP 배포에서는 비활성 |
| SES | Sandbox에서 검증된 발신·수신 주소만 사용 |
| 고가용성 | 단일 EC2이므로 호스트 장애 생존을 주장하지 않음 |
| 다중 Web·Worker | 13-5의 상태 공유·정합성 실험으로 분리하고 기본 용량 수치와 섞지 않음 |
| 자동 확장·다중 호스트·다중 리전 | 이번 포트폴리오 운영 검증에서 제외 |
| RDS·로드 밸런서·NAT Gateway·관리형 관측 서비스 | 비용 경계에 따라 생성하지 않음 |
| 장기 월간 가용성 실적 | 단기 실험으로 달성했다고 주장하지 않고 설계 목표만 제시 |

## 5. 기본 측정 환경

다음 값은 개선 전후의 기본 성능 비교에서 고정한다. EC2 세션을 시작할 때
실제 값을 다시 수집하고 다르면 측정 전에 원복하거나 새 기준으로 명시한다.

| 영역 | 고정 기준 |
|---|---|
| 리전 | AWS 서울 `ap-northeast-2` |
| 컴퓨팅 | 온디맨드 x86_64 `t3.medium`, 2 vCPU, 약 4GiB 메모리 |
| CPU 크레딧 | T3 Standard, Unlimited 사용 안 함 |
| 디스크 | 기존 gp3 16GiB, 측정 중 크기 변경 안 함 |
| 운영체제 | 13-0에서 확인한 Ubuntu 26.04 LTS x86_64, 세션 시작 시 재기록 |
| .NET | Web·Worker 모두 .NET 10 계열의 같은 release 산출물 |
| 공개 경계 | Nginx 80·443만 공개, Web과 데이터 서비스는 loopback |
| Web·Worker | 기본 용량 측정은 Web 1개, Worker 1개 |
| PostgreSQL | `postgres:18`, 같은 named volume과 같은 앱 역할·pool 설정 |
| Redis | `redis:8.8.1-alpine`, AOF `appendonly yes` |
| RabbitMQ | `rabbitmq:4.3.4-management-alpine`, 같은 queue·consumer 설정 |
| 객체 저장소 | Cloudflare R2 Standard 비공개 버킷 1개 |
| 이메일 | AWS SES 서울 리전 Sandbox |
| 관측 | 13-2에서 확정한 동일한 Collector·sampling·dashboard 설정 |
| 부하 발생기 | EC2 외부의 같은 로컬 PC, 같은 k6 버전과 네트워크 종류 |

자동 할당 공인 IP와 인증서는 세션마다 바뀔 수 있다. 이는 비용 정책에 따른
배포 주소 변경이며, 리전·인스턴스·부하 발생 위치가 같다면 성능 구성 변경으로
분류하지 않는다. 각 run에는 실제 URL과 인증서 검증 시각을 남긴다.

## 6. 비교에서 반드시 같아야 하는 값

개선 전 기준 측정과 개선 후 재측정은 다음 값을 동일하게 유지한다.

- EC2 종류, CPU 크레딧 모드와 데이터 서비스 이미지
- Web·Worker 인스턴스 수와 역할별 설정
- OpenTelemetry 계측, sampling과 수집 주기
- seed 데이터의 사용자·게임·드롭·키 수량과 검색 분포
- k6 시나리오, 단계, 유지 시간, threshold와 계정 준비 방식
- warm-up·측정·cool-down 구간과 UTC 시각 기록 방식
- 실행 전 queue·Outbox·Redis·DB 초기 상태와 실행 후 정합성 감사

13-5의 다중 프로세스 결과는 `topology=multi-same-host`, 기본 용량 측정은
`topology=single`로 표시한다. 두 결과를 하나의 개선 전후 표에 섞지 않는다.

## 7. 변경 통제

1. 최초 기준 부하 전에는 관측·부하·백업·장애 도구와 안전한 계측만 추가할
   수 있다. 사용자 기능 동작이 바뀌면 기준선 변경 사유를 기록한다.
2. 하나의 부하 사다리를 실행하는 동안 코드, DB 설정, Web·Worker 수와
   Collector 설정을 바꾸지 않는다.
3. 정합성 또는 보안 결함이 발견되면 성능 실험을 중단하고 먼저 수정한다.
   수정 전 결과는 용량 기준에서 제외한다.
4. 13-6의 성능 개선은 관측 증거가 지목한 병목 한 건만 적용한다. 다른 정리나
   리팩터링은 개선 commit에 섞지 않는다.
5. 환경 또는 도구 문제로 결과가 무효가 되면 좋은 구간만 골라 쓰지 않고
   무효 사유와 재실행 범위를 함께 남긴다.

## 8. 13-1-1 완료 기준

- 현재 기능 기준선과 마지막 실제 배포 commit이 구분되어 있다.
- 포함·제외 기능과 출시 판단 범위가 명시되어 있다.
- 기본 단일 프로세스와 13-5 다중 프로세스 실험이 분리되어 있다.
- 개선 전후에 고정할 인프라·데이터·부하 조건이 명시되어 있다.
- 최초 측정과 병목 개선 commit을 run manifest에서 고정하는 규칙이 있다.

## 9. SLI 정의

### 9.1. 공통 HTTP

| SLI | 계산 |
|---|---|
| 처리량 | 측정 구간의 완료 요청 수 / 측정 초 |
| 시스템 오류율 | timeout·network error·예상하지 않은 5xx / 전체 요청 |
| p50·p95·p99 | 시나리오·route별 end-to-end 응답시간 백분위 |
| 포화 | CPU·메모리·DB pool·lock·queue 중 안전선을 먼저 넘긴 자원 |

리다이렉트를 포함하는 폼 흐름은 POST 시작부터 최종 HTML 응답까지를 사용자
응답시간으로 잰다. `SoldOut`, `AlreadyClaimed`, `NotEligible`, validation 4xx처럼
명세에 정의된 결과는 시스템 오류가 아니다. 로그인 실패, antiforgery 실패,
예상하지 않은 4xx·5xx와 timeout은 부하 도구 또는 준비 오류로 따로 분류한다.

### 9.2. 사용자 흐름별 SLI

| 흐름 | 처리량·규모 | 지연 | 성공·정합성 |
|---|---|---|---|
| 공개 조회 | route별 RPS | p50·p95·p99 | 기대 HTML과 2xx, 시스템 오류율 |
| 검색 | query 조합별 RPS | p50·p95·p99 | 결과·cursor 유효성, 시스템 오류율 |
| 대기실 | 동시 참가자, 입장 처리량 | 참여·상태 조회 p95·p99 | 순번 단조성, terminal 상태 수렴 |
| 키 수령 | claim 시도·완료 RPS | POST→최종 화면 p50·p95·p99 | 지급 수≤키 수, 사용자·키당 단일 지급 |
| 알림 | 발행·소비 수, queue depth | DB 확정→알림 row p95 | Inbox 중복 없음, 최종 적체 0 |
| 미디어 | 처리 수, queue depth | 완료→Ready p50·p95 | 단일 current, 파생본·DB 상태 일치 |

### 9.3. 복구와 가용성 SLI

| SLI | 시작 | 종료 |
|---|---|---|
| 장애 감지시간 | 의존성 중단 명령 완료 | readiness·경보가 장애를 표시 |
| RTO | 장애 또는 복원 시작 | 합의한 사용자 흐름과 정합성 검사 성공 |
| RPO | 복원된 최신 데이터 시각 | 장애 직전 마지막 확정 데이터 시각과의 차이 |
| 실험 가용성 | 측정 구간 전체 | 성공한 기대 요청 시간 / 전체 측정 시간 |

월간 가용성은 단기 실험의 SLI로 계산하지 않는다. 실험에서 얻은 장애 감지와
복구시간을 바탕으로 13-7에서 설계 목표와 한계를 별도로 제시한다.

## 10. 검증 전 초기 목표

아래 값은 결과를 보기 전에 세운 가설이다. `초기 출시 목표`는 현재 단일 EC2가
안정적으로 통과하길 기대하는 수준, `부하 검증 목표`는 한계 탐색에서 반드시
시도할 수준, `구조 변경 없는 확장 목표`는 같은 구성에서 관찰할 상한 후보다.
검증 뒤 수치는 이 표를 덮어쓰지 않고 별도 열이나 결과 문서에 추가한다.

| 흐름 | 초기 출시 목표 | 부하 검증 목표 | 구조 변경 없는 확장 목표 |
|---|---|---|---|
| 공개 조회 | 25 RPS, p95≤500ms, p99≤1,000ms | 50 RPS | 100 RPS |
| 검색 | 10 RPS, p95≤750ms, p99≤1,500ms | 25 RPS | 50 RPS |
| 대기실 참여 | 동시 300명, p95≤500ms, p99≤1,000ms | 동시 1,000명 | 동시 2,000명 |
| 키 수령 집중 | 50 RPS, p95≤1,000ms, p99≤2,000ms | 100 RPS | 200 RPS |

공통 시스템 오류율의 초기 목표는 1% 미만이다. stress 단계는 한계를 찾는
실험이므로 이 목표를 넘을 수 있지만, 오류가 증가하기 직전 단계와 회복 여부를
반드시 기록한다. 모든 단계에서 키 초과 지급·중복 지급과 원장 불일치는 0건이어야
하며, 하나라도 발생하면 성능 수치와 관계없이 실패다.

비동기 흐름의 초기 목표는 다음과 같다.

| 흐름 | 초기 목표 |
|---|---|
| 사용자 알림 | DB 사건 확정 뒤 알림 row 생성 p95≤5초, 종료 후 queue·Outbox 적체 0 |
| 미디어 | 업로드 완료 뒤 Ready p95≤30초, 종료 후 처리 중·삭제 대기 상태 0 |
| SES 이메일 | 정상 공급자 상태에서 발송 대상 확정 뒤 전달 시도 p95≤60초 |

## 11. 검증 전 복구 목표

| 대상 | 초기 RPO | 초기 RTO | 의미 |
|---|---:|---:|---|
| PostgreSQL·R2·보호 키 묶음 | 24시간 | 2시간 | 하루 1회 정합 백업과 빈 환경 사용자 흐름 복원 |
| Redis 대기 상태 | 약 1초 | 15분 | AOF `everysec` 복구, 실패 시 대기열 재진입 안내 |
| RabbitMQ·Outbox | 확정 DB 사건 0건 손실 | 15분 | broker 복구 뒤 미발행 사건과 queue 수렴 |
| Web·Worker 프로세스 | 확정 DB 데이터 0건 손실 | 5분 | systemd 재시작 뒤 readiness·consumer 복구 |

초기 월간 가용성 설계 목표는 사용자 기능 기준 99.0%로 둔다. 이는 실제 운영
실적이나 단일 EC2의 보장이 아니다. 13-7에서 측정된 복구시간, 수동 개입과 단일
호스트 한계를 반영해 유지·수정·기각한다.

## 12. 작업 부하 모델

### 12.1. 공통 실행 순서

모든 시나리오는 다음 순서를 지킨다.

1. run id 생성과 기준 commit·환경 기록
2. 전용 seed 데이터 생성과 queue·Outbox 기준선 확인
3. 필요한 계정 로그인·CSRF·쿠키 준비
4. 낮은 요청의 warm-up
5. 고정된 measurement 단계 실행
6. 요청을 멈춘 cool-down과 비동기 작업 수렴 대기
7. DB·Redis·RabbitMQ·R2 정합성 감사와 증거 저장

로그인 준비와 seed는 measurement에 포함하지 않는다. 로그인 비밀번호 해시 CPU와
데이터 생성 쿼리를 사용자가 실제로 재려는 조회·키 수령 병목과 섞지 않기 위해서다.

### 12.2. W0 — smoke

- 목적: 주소·TLS·인증·결과 분류와 관측 연결 확인
- 부하: 시나리오별 1~5 VU 또는 1 RPS, 30초 이내
- 통과: 준비 실패 0건, 기대 결과와 trace·metric·log가 같은 run id로 확인됨
- 실패 시: calibration과 그 이후 단계를 실행하지 않음

### 12.3. W1 — 공개 조회 지속 부하

도착률을 고정하는 open model로 실행한다. 각 요청은 독립 방문으로 보고 응답이
느려져도 다음 요청 도착률을 자동으로 낮추지 않는다.

| 단계 | 목표 RPS | 유지 시간 |
|---|---:|---:|
| warm-up | 5 | 60초 |
| release | 25 | 120초 |
| validation | 50 | 120초 |
| stress-1 | 75 | 120초 |
| stress-2 | 100 | 120초 |

요청 비율은 홈·게임 목록 25%, 게임 상세 40%, 공개 프로필 15%, 다음 cursor 페이지
20%를 초기값으로 둔다. stress 단계는 앞 단계의 중단 조건이 발생하지 않을 때만
진행한다.

### 12.4. W2 — 검색 지속 부하

검색만의 DB 실행 계획과 인덱스 효과를 분리하기 위해 W1과 별도로 실행한다.

| 단계 | 목표 RPS | 유지 시간 |
|---|---:|---:|
| warm-up | 2 | 60초 |
| release | 10 | 120초 |
| validation | 25 | 120초 |
| stress | 50 | 120초 |

검색 입력은 제목·소개 토큰 40%, 장르·태그·플랫폼 조합 35%, 정렬·다음 cursor
25%로 구성한다. 존재하는 결과, 결과 없음과 한글·영문 검색어를 seed manifest에
고정하고 유효성 오류를 유발하는 입력은 성능 측정에서 제외한다.

### 12.5. W3 — 대기실 오픈 순간 유입

서로 다른 계정이 오픈 전 페이지와 로그인을 준비한 뒤 같은 절대 UTC 시각에
참여한다. cohort별로 새 드롭을 사용한다.

| 단계 | 동시 사용자 | 목적 |
|---|---:|---|
| smoke | 10 | 흐름·분류 확인 |
| release | 300 | 초기 출시 목표 |
| calibration | 500 | 부하 발생기·Redis 확인 |
| validation | 1,000 | 검증 목표 |
| stress-1 | 1,500 | 확장 후보 |
| stress-2 | 2,000 | 구조 변경 없는 상한 후보 |

각 cohort는 참여 결과, 순번 범위, 입장 허용 수와 terminal 상태 수렴을 감사한다.
로컬 부하 발생기가 필요한 VU를 준비하지 못하면 서버 한계로 기록하지 않고 해당
단계를 무효 처리한다.

### 12.6. W4 — 입장 허용 뒤 키 수령 집중

로그인과 대기실 참여를 완료한 전용 계정만 사용한다. 절대 UTC 시각에 입장 허용된
사용자를 짧은 구간에 배치해 25→50→100→200 claim RPS 후보를 순서대로 시험한다.
각 단계는 최소 10초 또는 준비된 사용자 소진까지 유지하고 별도 드롭을 사용한다.

키 수는 claim 사용자보다 적게 두어 `Granted`와 `SoldOut`을 함께 관측하되, 정확한
비율은 run manifest에 남긴다. 같은 계정의 의도적 재시도 cohort를 따로 두어
`AlreadyClaimed` 멱등 결과를 확인하고 신규 지급 처리량에는 합산하지 않는다.

### 12.7. W5 — 혼합 부하와 비동기 수렴

단일 시나리오의 안전 단계를 확인한 뒤에만 공개 조회·검색과 키 배포를 함께 실행한다.
초기 혼합 비율은 공개 조회 60%, 검색 20%, 대기실 상태 15%, claim 5%로 둔다.
알림과 미디어는 별도의 인위적 대량 요청을 섞기보다 도메인 사건에서 자연스럽게
발생한 queue·Worker 지연을 측정한다.

혼합 단계 종료 뒤 최대 5분 동안 새 요청을 보내지 않고 Outbox·RabbitMQ queue,
알림 delivery와 미디어 상태가 0 또는 합의한 terminal 상태로 수렴하는지 확인한다.

## 13. 단계 진행 규칙

- 각 단계는 최소 1회 예행 뒤 유효한 측정을 3회 반복하는 것을 원칙으로 한다.
- 동일 단계 3회 중 p95·처리량이 10% 넘게 흔들리면 환경·부하 발생기부터 조사한다.
- 다음 단계는 직전 단계가 중단 조건 없이 끝나고 정합성 감사에 통과했을 때만 실행한다.
- 최초 중단 단계 이후 더 높은 단계는 실행하지 않고 cool-down과 복구를 확인한다.
- stress 실패는 제품 결함과 동일하지 않다. 직전 안정 단계와 실패 원인을 함께 기록한다.

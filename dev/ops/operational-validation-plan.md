# 운영 검증 기준과 측정 계약

## 1. 목적

이 문서는 로드맵 13-1부터 13-7까지 수행할 운영 검증의 비교 기준을
소유한다. 성능 수치는 코드뿐 아니라 서버 사양, 데이터 크기, 실행 프로세스
수와 부하 발생 방식에 따라 달라진다. 따라서 결과를 보기 전에 검증 범위와
고정 조건을 기록하고, 조건이 달라진 실행은 별도 실험으로 취급한다.

관련 문서:

- 기능 범위: `docs/functional-specification-v2.md` 13장
- 실행 순서: `docs/functional-specification-v2-roadmap.md` 13장
- 비용·종료 기준: `dev/ops/portfolio-deployment-cost-runbook.md`
- 배포 구조: `dev/ops/portfolio-runtime-runbook.md`

## 2. 기준 버전

| 구분 | commit | 의미 |
|---|---|---|
| 마지막 운영 스모크 테스트 배포 | `002fc171d8ebec57957b4c86d0179b338768334b` | 13-0에서 실제 EC2 기능 연결을 확인한 버전 |
| 현재 기능 기준선 | `a486bc3920a42d13bfa4eea7c63b7aae4f2eea87` | UI/UX 최종화를 포함해 13-1을 시작한 `dev` HEAD |
| 최초 성능 기준 측정 | 13-2 계측 완료 뒤 run manifest에 기록 | OpenTelemetry를 포함한 실제 기준 부하 버전 |
| 병목 개선 재측정 | 13-6-8 완료 뒤 run manifest에 기록 | 기준 측정에서 찾은 병목 한 건만 개선한 버전 |

`002fc17`은 현재 기능 기준선의 조상이며 과거 배포 증거다. 앞으로 수행하는
성능 비교는 `002fc17`과 하지 않는다. 13-2의 계측 변경을 포함한 최초 측정
commit과 13-6-8의 단일 개선 commit을 비교한다.

각 실행은 짧은 hash가 아니라 전체 commit SHA를 결과 manifest에 남긴다.
측정 도중 코드나 런타임 설정이 바뀌면 같은 run으로 이어서 기록하지 않는다.

## 3. 검증에 포함하는 기능

관리자 기능을 제외한 현재 사용자 기능을 검증한다.

1. 이메일·비밀번호 가입, 이메일 확인, 로그인, 세션, 비밀번호 변경·재설정
2. 게임 등록·수정, 분류, 플레이 링크, 공개 목록·검색·상세 조회
3. 프로필, 팔로우와 관심 게임
4. 크레딧 원장, 리뷰 요청·배정·제출·평가와 리뷰어 평판
5. 키 배포 예약·재고·대기실·입장 허용·암호화된 키 지급
6. Outbox, RabbitMQ, Worker, 웹·실시간·SES 알림
7. R2 직접 업로드, Worker 이미지 처리, 공개 조회와 삭제
8. Nginx HTTPS, Web·Worker systemd와 PostgreSQL·Redis·RabbitMQ 실행 경계

일반 부하는 공개 조회·검색, 집중 부하는 대기실·키 수령을 대표 시나리오로
사용한다. 알림과 미디어는 사용자 부하의 후속 비동기 처리량과 장애 복구를
별도로 관측한다.

## 4. 검증에서 제외하거나 제한하는 범위

| 항목 | 처리 |
|---|---|
| 로드맵 5 관리자 기능 | 미구현이므로 출시 판단 범위에서 제외 |
| Google 로그인 | 제품 기능은 유지하지만 원시 IP 배포에서는 비활성 |
| SES | Sandbox에서 검증된 발신·수신 주소만 사용 |
| 고가용성 | 단일 EC2이므로 호스트 장애 생존을 주장하지 않음 |
| 다중 Web·Worker | 13-5의 상태 공유·정합성 실험으로 분리하고 기본 용량 수치와 섞지 않음 |
| 자동 확장·다중 호스트·다중 리전 | 이번 포트폴리오 운영 검증에서 제외 |
| RDS·로드 밸런서·NAT Gateway·관리형 관측 서비스 | 비용 경계에 따라 생성하지 않음 |
| 장기 월간 가용성 실적 | 단기 실험으로 달성했다고 주장하지 않고 설계 목표만 제시 |

## 5. 기본 측정 환경

다음 값은 개선 전후의 기본 성능 비교에서 고정한다. EC2 세션을 시작할 때
실제 값을 다시 수집하고 다르면 측정 전에 원복하거나 새 기준으로 명시한다.

| 영역 | 고정 기준 |
|---|---|
| 리전 | AWS 서울 `ap-northeast-2` |
| 컴퓨팅 | 온디맨드 x86_64 `t3.medium`, 2 vCPU, 약 4GiB 메모리 |
| CPU 크레딧 | T3 Standard, Unlimited 사용 안 함 |
| 디스크 | 기존 gp3 16GiB, 측정 중 크기 변경 안 함 |
| 운영체제 | 13-0에서 확인한 Ubuntu 26.04 LTS x86_64, 세션 시작 시 재기록 |
| .NET | Web·Worker 모두 .NET 10 계열의 같은 release 산출물 |
| 공개 경계 | Nginx 80·443만 공개, Web과 데이터 서비스는 loopback |
| Web·Worker | 기본 용량 측정은 Web 1개, Worker 1개 |
| PostgreSQL | `postgres:18`, 같은 named volume과 같은 앱 역할·pool 설정 |
| Redis | `redis:8.8.1-alpine`, AOF `appendonly yes` |
| RabbitMQ | `rabbitmq:4.3.4-management-alpine`, 같은 queue·consumer 설정 |
| 객체 저장소 | Cloudflare R2 Standard 비공개 버킷 1개 |
| 이메일 | AWS SES 서울 리전 Sandbox |
| 관측 | 13-2에서 확정한 동일한 Collector·sampling·dashboard 설정 |
| 부하 발생기 | EC2 외부의 같은 로컬 PC, 같은 k6 버전과 네트워크 종류 |

자동 할당 공인 IP와 인증서는 세션마다 바뀔 수 있다. 이는 비용 정책에 따른
배포 주소 변경이며, 리전·인스턴스·부하 발생 위치가 같다면 성능 구성 변경으로
분류하지 않는다. 각 run에는 실제 URL과 인증서 검증 시각을 남긴다.

## 6. 비교에서 반드시 같아야 하는 값

개선 전 기준 측정과 개선 후 재측정은 다음 값을 동일하게 유지한다.

- EC2 종류, CPU 크레딧 모드와 데이터 서비스 이미지
- Web·Worker 인스턴스 수와 역할별 설정
- OpenTelemetry 계측, sampling과 수집 주기
- seed 데이터의 사용자·게임·드롭·키 수량과 검색 분포
- k6 시나리오, 단계, 유지 시간, threshold와 계정 준비 방식
- warm-up·측정·cool-down 구간과 UTC 시각 기록 방식
- 실행 전 queue·Outbox·Redis·DB 초기 상태와 실행 후 정합성 감사

13-5의 다중 프로세스 결과는 `topology=multi-same-host`, 기본 용량 측정은
`topology=single`로 표시한다. 두 결과를 하나의 개선 전후 표에 섞지 않는다.

## 7. 변경 통제

1. 최초 기준 부하 전에는 관측·부하·백업·장애 도구와 안전한 계측만 추가할
   수 있다. 사용자 기능 동작이 바뀌면 기준선 변경 사유를 기록한다.
2. 하나의 부하 사다리를 실행하는 동안 코드, DB 설정, Web·Worker 수와
   Collector 설정을 바꾸지 않는다.
3. 정합성 또는 보안 결함이 발견되면 성능 실험을 중단하고 먼저 수정한다.
   수정 전 결과는 용량 기준에서 제외한다.
4. 13-6의 성능 개선은 관측 증거가 지목한 병목 한 건만 적용한다. 다른 정리나
   리팩터링은 개선 commit에 섞지 않는다.
5. 환경 또는 도구 문제로 결과가 무효가 되면 좋은 구간만 골라 쓰지 않고
   무효 사유와 재실행 범위를 함께 남긴다.

## 8. 13-1-1 완료 기준

- 현재 기능 기준선과 마지막 실제 배포 commit이 구분되어 있다.
- 포함·제외 기능과 출시 판단 범위가 명시되어 있다.
- 기본 단일 프로세스와 13-5 다중 프로세스 실험이 분리되어 있다.
- 개선 전후에 고정할 인프라·데이터·부하 조건이 명시되어 있다.
- 최초 측정과 병목 개선 commit을 run manifest에서 고정하는 규칙이 있다.

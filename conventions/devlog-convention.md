# 개발 일지 컨벤션

> 기능 하나가 끝날 때 **1편**을 남긴다.
> ⚠️ **개인 문서다 — 커밋하지 않는다.** 위치는 `docs/devlog/`(루트 `.gitignore`의 `docs/` 규칙에 걸림).
> 목적: *무엇을 왜 했고, 무엇을 겪었나*를 나중에 읽어도 따라갈 수 있게 남긴다.

## 왜 커밋하지 않나

저장소에는 **실제 프로젝트 산출물**(`dev/` 코드, `conventions/`)만 올린다. 개발 일지는 학습 기록·개인 회고가 섞인 문서라 `docs/`와 같은 취급이다. 나중에 공개용 글로 다듬고 싶으면 **그때 따로 정리해서** 내보낸다.

## 위치·파일명

- `docs/devlog/NNN-기능이름.md` (예: `docs/devlog/001-회원가입.md`)
- `NNN` = 3자리 순번(001부터).
- 첫 기능이 끝날 때 폴더째 만든다. 미리 빈 폴더를 만들지 않는다.

## 형식

```markdown
# NNN — <기능 이름>

- 날짜: YYYY-MM-DD
- 브랜치 / 커밋: <브랜치명> / <커밋 해시들>

## 무엇을 만들었나
<완성된 기능. 화면과 동작 기준으로.>

## 어떻게 돌아가나
<요청이 들어와서 응답이 나가기까지. 나중의 내가 읽고 따라갈 수 있게.>

## 왜 이렇게 했나
<선택과 이유. 버린 대안과 버린 이유.>

## 막힌 것 / 배운 것
<디버깅에서 배운 것. 예상과 달랐던 것. 다음으로 넘긴 것.>

## 다음
<이어서 할 것.>
```

성능 문제를 다룬 편이라면 아래를 추가한다. **이 프로젝트가 가장 남기고 싶어 하는 형태**다.

```markdown
## 느려진 것을 어떻게 찾았나
- 증상: <무엇이 얼마나 느렸나 / 얼마나 실패했나>
- 가설: <처음에 뭐라고 생각했나>
- 확인 방법: <어떤 도구로 어떻게 들여다봤나>
- 실제 원인: <가설이 맞았나 틀렸나>
- 고친 방법:
- 다시 재보니: <before → after 숫자>
```

## 규율

- **왜와 겪은 일 중심.** 무엇(코드)은 diff가 말해준다.
- 측정 없이 성능 주장 금지. "빨라졌다" ❌ → 숫자 ✅. 못 쟀으면 **"측정 못 함"이라고 정직히** 쓴다.
- **가설이 틀렸으면 틀렸다고 쓴다.** 틀린 가설을 측정이 고쳐준 기록이 이 일지에서 제일 값나가는 부분이다.
- 커밋 메시지와 달리 여기서는 내부 용어를 써도 된다(개인 문서라서). 다만 나중의 내가 못 알아볼 약어는 풀어 쓴다.
